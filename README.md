# Intelligent Secure CI/CD Pipeline with Shift-Left Security using Generative AI

A DevSecOps prototype that scans a project for vulnerabilities early in the
pipeline (shift-left), explains and prioritizes them using **both** a
generative AI model (Gemini) and a locally trained **dataset-driven ML
model**, gates deployment automatically, and improves itself over time
through a feedback loop — matching the architecture diagram below.

## Architecture -> Code Map

| Diagram box | What it means | Where it lives |
|---|---|---|
| **Developments** | Developers write and commit code | `vulnerable_target/`, `demo_app/` (sample projects being developed) |
| **CI/CD Pipelines** | Automates build, test, integration | `Jenkinsfile` |
| **Shift-Left Security** | Security checks at early stage | `Jenkinsfile` → Trivy stage runs before deployment, on every commit |
| **Security Scanning** | Continuous vulnerability detection | Trivy, invoked from `app.py` (`run_trivy`) and `Jenkinsfile` |
| **AI-Based Analysis** | Generative AI explains vulnerabilities, risks, fixes | `analyze_with_gemini()` in `app.py` / `ai_security_analyzer.py` |
| **Dataset-Driven Learning** | Vulnerability data → processing → training → AI model | `ml_model/train_model.py`, `ml_model/dataset/vulnerability_dataset.csv`, `ml_model/risk_model.py` |
| **Feedback Loop** | New data/results improve the AI model over time | `feedback/feedback_log.csv` (written every scan) + `feedback/retrain.py` |
| **Automated Deployment** | Docker for secure, consistent deployment | `Dockerfile.dashboard`, `demo_app/Dockerfile`, `docker-compose.yml` |
| **Deployed Application** | Secure, reliable e-commerce app is live | `demo_app/` (Flask storefront, hardened against the same bug classes Trivy/Gemini catch) |
| **Monitor and Improve** | Pipeline performance & security insights | `monitor/history.py` + the `/monitor` dashboard page |

There are genuinely **two** AI components, on purpose, because the diagram
draws them as separate boxes:

1. **AI-Based Analysis (generative AI)** — Gemini reads the raw Trivy
   report and source code and produces human-readable explanations and
   suggested fixes. Falls back to a deterministic local analyzer
   (`generate_fallback_findings`) if no `GEMINI_API_KEY` is set, so the demo
   always works offline.
2. **Dataset-Driven Learning (trained ML model)** — a `RandomForestClassifier`
   trained on `ml_model/dataset/vulnerability_dataset.csv` predicts a
   `LOW / MEDIUM / URGENT` priority for each finding from structured features
   (severity, whether it's a secret, whether a fix exists, CVE count,
   ecosystem). This doesn't need an API key or network access, and it is
   the piece the **feedback loop** actually retrains.

## Project layout

```
app.py                     Flask dashboard: upload/scan/analyze/gate + /monitor
ai_security_analyzer.py    CLI version run from Jenkins (Trivy report -> AI report)
Jenkinsfile                Full pipeline: checkout -> SAST -> Trivy -> AI analysis
                            -> security gate -> Docker deploy -> retrain -> monitor
ml_model/
  dataset/vulnerability_dataset.csv   Training data (extend this with real CVEs)
  train_model.py           Data processing + model training
  risk_model.py            Inference helper used by app.py
  model.pkl, metrics.json  Generated by train_model.py (not hand-edited)
feedback/
  feedback_log.csv         Every scan's findings, appended automatically
  retrain.py               Folds feedback_log.csv back into training data
monitor/
  history.py               SQLite-backed scan history for the /monitor page
demo_app/                  DEPLOYED APPLICATION: a small, secure e-commerce app
vulnerable_target/         Intentionally vulnerable sample app used to demo scanning
templates/, static/        Dashboard UI (index.html, monitor.html)
docker-compose.yml         Deploys dashboard + demo_app together
Dockerfile.dashboard       Containerizes the dashboard (includes Trivy + trained model)
```

## Running it locally

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Install Trivy (the vulnerability/secret scanner)
#    macOS:   brew install trivy
#    Linux:   curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh
#    Or just have Docker installed — app.py falls back to `docker run aquasec/trivy` automatically.

# 3. Train the dataset-driven risk model (produces ml_model/model.pkl)
python ml_model/train_model.py

# 4. (Optional) Set a Gemini API key for generative-AI explanations.
#    Without this, the app still works using a deterministic local analyzer.
export GEMINI_API_KEY=your_key_here

# 5. Run the dashboard
python app.py
# -> open http://127.0.0.1:5000
```

From the dashboard you can:
- Paste a public GitHub URL, or upload a ZIP, to scan a project.
- Watch the Security Gate block/allow "deployment" based on findings.
- See each finding's Gemini explanation **and** its ML-model priority.
- Open **Monitor & Improve** (top-right button, or `/monitor`) to see scan
  history trends and current model accuracy.

### Closing the feedback loop

Every scan appends rows to `feedback/feedback_log.csv`. To retrain the model
on everything collected so far:

```bash
python feedback/retrain.py
```

Or click "Update Project" / call `POST /api/retrain` from the dashboard —
`ml_model/model.pkl` and `ml_model/metrics.json` are refreshed in place, and
the next scan uses the updated model immediately.

### Running the full stack with Docker

```bash
docker compose up --build
# Dashboard:        http://localhost:5000
# Demo e-commerce:  http://localhost:5050
```

### Running the Jenkins pipeline

`Jenkinsfile` expects a `gemini-api-key` Jenkins credential and Docker + Trivy
available on the agent. It runs, in order: checkout → SonarQube static
analysis → Trivy scan → AI-based analysis (Gemini + ML risk model) →
security gate (fails the build on CRITICAL/HIGH) → Docker build & deploy →
feedback-loop retrain → monitor.

## What to extend next

1. **Grow the training dataset.** `ml_model/dataset/vulnerability_dataset.csv`
   currently has ~40 hand-crafted rows so the pipeline is fully runnable
   out of the box. Swap in real historical CVE/Trivy data (there's a public
   NVD feed) for a model that generalizes better than the current
   ~55% held-out test accuracy.
2. **Replace the proxy feedback label.** `log_feedback()` in `app.py`
   currently derives a training label from Trivy's own severity, since there's
   no human-verified outcome yet. A stronger version would let a reviewer
   mark each finding "fixed / false positive / ignored" in the dashboard and
   train on that instead — that's a much more honest feedback loop.
3. **Add SAST, not just Trivy.** The Jenkinsfile references SonarQube for
   static analysis — wire up a real SonarQube server (or Semgrep, as a
   lighter-weight alternative) so "Shift-Left Security" also catches
   insecure code patterns, not just dependency CVEs and secrets.
4. **Expand `demo_app/`.** It's intentionally minimal (products, signup,
   login) so it's easy to read end-to-end. A cart/checkout flow would give
   the "e-commerce application" more surface area for the scanner and a
   more convincing capstone demo.
5. **Real deployment target.** `docker-compose.yml` deploys locally; for a
   more complete "Automated Deployment" story, push built images to a
   registry and deploy to a small Kubernetes cluster or cloud run service
   as part of the Jenkins pipeline.
